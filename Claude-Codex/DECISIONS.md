# 架构决策记录 (DECISIONS.md)

> 每条记录一个重要技术决策及其理由，避免后人重复推翻已定的事。
> 格式：ADR-编号 | 标题 | 决策 | 理由 | 状态(采纳/废弃/取代)

## ADR-001 | AI 产出结构化剪辑计划，不操作剪辑软件
- **决策**: 系统所有环节围绕一份结构化 JSON（plan.json）读写；AI 负责生成/修改这份计划，渲染由确定性工具（FFmpeg/Remotion/Pillow）执行。
- **理由**: 让 AI 操作 GUI 剪辑软件不可控、不可复现、难自动化。结构化计划可版本化、可增量重渲染、可被前端可视化编辑——这正好支撑「手动修改成品」的需求。
- **状态**: 采纳（继承自现有 POC，验证有效）

## ADR-002 | 定位为「半自动 + 人工品控」
- **决策**: 内部架构按半自动设计，人卡在选题、终审、发布三个高价值节点。素材匹配、跨平台发布不强求 100% 自动。
- **理由**: 当前技术下，素材精准匹配和抖音/小红书/B站自动发布是硬瓶颈，强行全自动会翻车。对外可用「全自动」做营销，但工程不能赌它。
- **状态**: 采纳

## ADR-003 | 双 AI 协作：Claude 设计+审查，Codex 实现
- **决策**: Claude 担任 PM/架构/Reviewer，Codex 担任主力 Implementer。交接通过 Claude-Codex/ 目录的文件完成。
- **理由**: 写代码与审代码分离，减少自审盲点。Claude 长上下文适合握全局，Codex 适合专注落地。
- **状态**: 采纳

## ADR-004 | 素材策略：以「真实素材打标签+智能匹配」为主，AI 生成为辅
- **决策**: 优先要求商家上传真实素材，用视觉模型打标签后按脚本匹配；AI 生成视频仅作 B-roll 补充。
- **理由**: 现阶段 AI 生成视频无法精准还原真实产品/门店，做严肃推广不可靠。「智能筛选拼接」比「凭空生成」可靠得多，也契合「帮有素材但不会剪的商家」定位。
- **状态**: 采纳

## ADR-005 | 技术栈基线：后端 Python + 前端按需引 JS（渐进迁移）
- **决策**: 生成/渲染核心逻辑继续用 Python（复用现有 POC）；只在 M5 网页可视化编辑器等必须用 JS 的地方引入前端栈。不一次性推翻 Python 代码。
- **理由**: M1/M2/M3 本质是读写 JSON + 调 API + 渲染，Python 完全胜任且能复用现有正确架构。统一到 JS 的收益要到 M5 才显现，届时再评估。符合「不重写可用代码」原则。
- **状态**: 采纳（D-04 据此关闭）

## ADR-006 | 首个验证闭环只做 M1（LLM 生成）
- **决策**: 先把模板生成换成真 LLM 生成，不急着串 TTS/MP4。
- **理由**: 投入小、出效果快，脚本/分镜质量提升最直观，能最快验证「AI 生成内容是否够用」这个核心假设。
- **状态**: 采纳

## ADR-007 | M1 用手写校验，不引入 jsonschema
- **决策**: M1 阶段保留手写 `validate_generation` 校验关键字段；`video_project.schema.json` 作为「契约文档/真相来源」，但不作为运行时校验器。不引入 jsonschema 依赖。
- **理由**: Codex 按协议正确地没有擅自加依赖并提出此问题。M1 需校验的字段有限，手写够用且零依赖。代价是校验与契约可能漂移——通过「契约改动必须经 Claude 并记 ADR」的流程来约束，规模变大或字段复杂后再评估引入 jsonschema。
- **状态**: 采纳（回应 Codex 在 HANDOFF #3 提出的依赖问题）
