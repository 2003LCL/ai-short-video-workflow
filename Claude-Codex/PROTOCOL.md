# 协作协议 (Claude × Codex × 你)

> 这是整个项目的「交接规则」。任何一个 AI 接手工作前，**必须先按顺序读完本目录下的文件**，
> 再开始动手。两个 AI 没有共享记忆，磁盘上的文字是唯一的交接介质。

## 角色分工

| 角色 | 谁 | 职责 |
|---|---|---|
| 产品负责人 / 选题 / 品控 | **你（人类）** | 定方向、选题、终审视频、对接客户、做发布与合规决策 |
| 产品经理 / 架构 / 代码审查 | **Claude** | 写 PRD 和技术规格、定义模块接口契约、审查 Codex 的代码、把控架构一致性 |
| 主力开发 | **Codex** | 按 Claude 给出的任务规格和接口契约实现模块、写测试、修复 Review 中提出的问题 |

**核心原则：写代码的人和审代码的人不是同一个。** Claude 出题 + 批改，Codex 答题。

## 工作循环 (一个任务的完整生命周期)

```
1. Claude 写任务规格      → 写入 TASKS.md 的一条任务 (状态 TODO)
2. Codex 认领并实现       → 把状态改为 DOING，开工
3. Codex 完成            → 把状态改为 REVIEW，并在 HANDOFF.md 写交接说明
4. Claude 审查           → 通过则改为 DONE；不通过则写明问题、状态退回 DOING
5. 你（人类）验收关键节点  → 重大里程碑由你拍板
```

## 四个交接文件 (每次接手都先读这四个)

1. **`STATE.md`** — 项目当前状态快照：跑到哪了、整体进度、当前焦点。**每次动手前先读，收工前必更新。**
2. **`TASKS.md`** — 任务看板：所有任务及其状态 (TODO / DOING / REVIEW / DONE / BLOCKED)。
3. **`HANDOFF.md`** — 最近一次交接的详细说明：我改了什么、为什么这么改、下一个人该注意什么、有哪些坑。**这是「无缝跟上思路」的关键文件。**
4. **`DECISIONS.md`** — 架构决策记录 (ADR)：重要技术选择及其理由。避免后人重复推翻已定的事。

外加 `CONTRACTS/` 目录：存放模块之间的接口契约 (JSON Schema、函数签名约定)。**契约一旦定下，改动必须经 Claude 同意并记入 DECISIONS.md**，因为改契约会同时影响上下游多个模块。

## 交接说明 (HANDOFF.md) 的固定格式

每次收工，接力者必须按这个格式追加一段：

```markdown
## [日期] <角色> → <下一个角色>
**改动**: 一句话说清这次做了什么
**涉及文件**: 列出新增/修改的文件
**为什么这么做**: 关键决策的理由（让对方能跟上思路，而不只是看到结果）
**接口变化**: 是否动了 CONTRACTS/ 里的契约？动了哪条？
**验证情况**: 跑了什么测试/命令，结果如何；没验证的部分要说明
**下一步建议**: 下一个人最该做什么；已知的坑和未决问题
```

## 给 Codex 的硬性要求 (Claude 在每个任务规格里会重申)

- 严格按 `CONTRACTS/` 里的接口契约读写数据，不要擅自改 JSON 结构。
- 每个模块要能**独立运行、独立测试、产物落盘**，失败能从中断处重跑。
- 不引入未在 DECISIONS.md 里批准的新依赖/新框架。
- 完成后必须更新 STATE.md、TASKS.md，并在 HANDOFF.md 写交接说明。
- 匹配现有代码风格（看 run_workflow.py），不重写已有可用代码。

## 给 Claude 的硬性要求 (审查时)

- 审逻辑正确性、接口契约符合度、边界情况、错误处理，而不只是看跑没跑通。
- 发现问题写清楚「哪一行、什么问题、怎么改」，退回时状态明确。
- 任何架构层面的调整都要记进 DECISIONS.md。
