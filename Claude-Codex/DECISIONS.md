# 架构决策记录 (DECISIONS.md)

> 每条记录一个重要技术决策及其理由，避免后人重复推翻已定的事。
> 格式：ADR-编号 | 标题 | 决策 | 理由 | 状态(采纳/废弃/取代)

## ADR-001 | AI 产出结构化剪辑计划，不操作剪辑软件
- **决策**: 系统所有环节围绕一份结构化 JSON（plan.json）读写；AI 负责生成/修改这份计划，渲染由确定性工具（FFmpeg/Remotion/Pillow）执行。
- **理由**: 让 AI 操作 GUI 剪辑软件不可控、不可复现、难自动化。结构化计划可版本化、可增量重渲染、可被前端可视化编辑——这正好支撑「手动修改成品」的需求。
- **状态**: 采纳（继承自现有 POC，验证有效）

## ADR-002 | 定位为「半自动 + 人工品控」
- **决策**: 内部架构按半自动设计，人卡在选题、终审、发布三个高价值节点。素材匹配、跨平台发布不强求 100% 自动。
- **理由**: 当前技术下，素材精准匹配和抖音/小红书/B站自动发布是硬瓶颈，强行全自动会翻车。对外可用「全自动」做营销，但工程不能赌它。
- **状态**: 采纳

## ADR-003 | 双 AI 协作：Claude 设计+审查，Codex 实现
- **决策**: Claude 担任 PM/架构/Reviewer，Codex 担任主力 Implementer。交接通过 Claude-Codex/ 目录的文件完成。
- **理由**: 写代码与审代码分离，减少自审盲点。Claude 长上下文适合握全局，Codex 适合专注落地。
- **状态**: 采纳

## ADR-004 | 素材策略：以「真实素材打标签+智能匹配」为主，AI 生成为辅
- **决策**: 优先要求商家上传真实素材，用视觉模型打标签后按脚本匹配；AI 生成视频仅作 B-roll 补充。
- **理由**: 现阶段 AI 生成视频无法精准还原真实产品/门店，做严肃推广不可靠。「智能筛选拼接」比「凭空生成」可靠得多，也契合「帮有素材但不会剪的商家」定位。
- **状态**: 采纳

## ADR-005 | 技术栈基线：后端 Python + 前端按需引 JS（渐进迁移）
- **决策**: 生成/渲染核心逻辑继续用 Python（复用现有 POC）；只在 M5 网页可视化编辑器等必须用 JS 的地方引入前端栈。不一次性推翻 Python 代码。
- **理由**: M1/M2/M3 本质是读写 JSON + 调 API + 渲染，Python 完全胜任且能复用现有正确架构。统一到 JS 的收益要到 M5 才显现，届时再评估。符合「不重写可用代码」原则。
- **状态**: 采纳（D-04 据此关闭）

## ADR-006 | 首个验证闭环只做 M1（LLM 生成）
- **决策**: 先把模板生成换成真 LLM 生成，不急着串 TTS/MP4。
- **理由**: 投入小、出效果快，脚本/分镜质量提升最直观，能最快验证「AI 生成内容是否够用」这个核心假设。
- **状态**: 采纳

## ADR-007 | M1 用手写校验，不引入 jsonschema
- **决策**: M1 阶段保留手写 `validate_generation` 校验关键字段；`video_project.schema.json` 作为「契约文档/真相来源」，但不作为运行时校验器。不引入 jsonschema 依赖。
- **理由**: Codex 按协议正确地没有擅自加依赖并提出此问题。M1 需校验的字段有限，手写够用且零依赖。代价是校验与契约可能漂移——通过「契约改动必须经 Claude 并记 ADR」的流程来约束，规模变大或字段复杂后再评估引入 jsonschema。
- **状态**: 采纳（回应 Codex 在 HANDOFF #3 提出的依赖问题）

## ADR-008 | 渲染引擎：M3 先用 FFmpeg/MoviePy 出 MP4，Web 编辑器阶段(M5)再引入 Remotion
- **决策**: M3「图片+字幕+配音合成 MP4」用 FFmpeg/MoviePy（纯 Python，复用现有 Pillow 运镜逻辑）。等到 M5 做网页可视化编辑器时，再引入 Remotion 承担「所见即所得预览 + 数据驱动局部重渲染」。可能长期两者并存：Python 管 AI 编排与批量渲染，Remotion 管 Web 编辑与预览。
- **理由**（基于 2026-06 调研）:
  - FFmpeg 8.0(2025-08)活跃、商用免费(LGPL/GPL)，MoviePy(MIT) 原生 Python 集成零摩擦，单机渲染轻量快。M3 阶段还没有 Web 编辑器，没必要为它引入 Node/React 链路和 Headless Chrome 的渲染开销。
  - Remotion 的杀手锏(`@remotion/player` 实时预览 + props 数据驱动 + 局部重渲染)只有到 M5 才用得上；它许可受限(4 人以上公司需购席位 license)、渲染开销大(逐帧跑 Chrome)、且是 Node 进程需跨语言桥接。
  - 结论：按里程碑需要分阶段引入，不预先锁死，避免过早承担 Remotion 的成本与约束。
- **状态**: 采纳（关闭 D-02。注：Remotion 公司版具体席位价格未在调研中确认，真要商用前需到官网核对）

## ADR-009 | TTS：M2 先用云 API（阿里云百炼 CosyVoice / 火山引擎），起量后切自部署 CosyVoice
- **决策**: M2 接 TTS 先走云 API（首选阿里云百炼 CosyVoice，同源托管、中文自然、支持音色复刻、免运维、按量付费；火山引擎为备选）。当口播字数规模上来、账单可观时，再切换到自部署 CosyVoice 2/3 (0.5B) 把边际成本压到接近零。
- **理由**（基于 2026-06 调研）:
  - 「先云后私」是这类项目的自然演进：起步期免运维、按量付费最省心，对接 Python 后端简单；规模化后自部署边际成本趋零、音色资产自有。
  - CosyVoice 中文自然度在开源第一梯队，0.5B 消费级 GPU 可跑，云/私同源便于平滑迁移。
  - ElevenLabs 中文非最强项 + 美元成本/访问合规，性价比不突出，排靠后。
- **未决细节**: 各云 TTS 每字符单价、CosyVoice 权重商用条款，下单/上线前需到官网二次确认（调研中被网络策略拦截未取到精确数字）。音色克隆真人声音涉及授权合规。
- **状态**: 采纳（关闭 D-03）

## ADR-010 | M2 契约升级 + 批准 edge-tts 依赖
- **决策**:
  1. 契约升级(video_project.schema.json)：scene 新增 `voiceover_audio`(file/audio_duration/provider/voice)，顶层新增 `audio` 汇总块。这是 M2 的 TTS 产物落点。
  2. 批准引入免费依赖 `edge-tts`(无需 key，调微软在线 Neural 语音)，用于 M2 试效果。
- **理由**: 配音音频需要在数据结构里有明确落点，才能被 M3 渲染消费、被 M5 编辑器引用。edge-tts 零成本零门槛，是验证「AI 中文口播效果是否够用」的最快方式。注意：edge-tts 走微软非公开接口，仅试水用，商用按 ADR-009 切阿里云 CosyVoice。
- **状态**: 采纳

## ADR-011 | 先打通全流程闭环，文案质量优化推迟到最后；文案在 M5 编辑器做成可改
- **决策**: 优先把 M1→M3 全流程闭环跑通，**不在中途停下来做文案质量专项**。文案优化推迟到闭环完成后再回炉。同时，文案在 M5 网页编辑器里做成**客户可手动修改**的半成品（改脚本/换语气/调字幕），不追求 AI 一次生成完美。
- **理由**: (1) 先验证整条管道能产出成品，比局部打磨某一环更重要——闭环不通时优化文案是无的放矢。(2) 产品定位本就是「半自动 + 人工品控」(ADR-002)，AI 出半成品、客户网页微调，正好咬合这个定位，也降低对 AI 文案完美度的依赖。(3) 用户已确认 AI 配音效果够用、文案才是重点，但重点不等于现在做——留到闭环后集中优化收益更高。
- **影响**: 之前 HANDOFF #10 提的「文案质量专项」从「独立专项」调整为「M5 编辑器自带能力 + 闭环后回炉优化」两部分。M1 mock 文案维持现状即可，不为它单独返工。
- **状态**: 采纳

## ADR-012 | M3 渲染依赖：MoviePy + imageio-ffmpeg，复用现有运镜/叠层逻辑
- **决策**:
  1. 批准引入 `moviepy`(MIT) 与 `imageio-ffmpeg`(自带静态 ffmpeg 二进制) 两个依赖，用于 M3 把帧序列 + 配音合成 MP4。
  2. MP4 渲染**复用** `render_gif_preview` 里已验证的 `_ken_burns_crop`(运镜) 和叠层绘制逻辑，把「场景+进度→一帧」抽成 GIF/MP4 共享函数，不复制粘贴、不重调版面常量。
  3. MP4 分辨率直接用现有「超采样帧」(预览画布 × ss，如 9:16 → 720×1280)，绕开版面重调，零摩擦达到 720p。
  4. **不升级契约**：产物登记进 v1 契约已预埋的顶层 `renders[]`(kind:"mp4")，无需改 schema。
- **理由**（落实 ADR-008）:
  - ADR-008 已定 M3 用 FFmpeg/MoviePy；imageio-ffmpeg 自带二进制让 Windows 免装系统 ffmpeg，是这个阶段最省事的落地方式。MoviePy 处理「逐段音频按时间定位 + 静音留白 + 合并音视频」零摩擦。
  - 复用现有渲染逻辑而非另起一套，保证 MP4 与 GIF/HTML 预览视觉一致，也符合「不重写可用代码」原则。
  - Remotion 仍按 ADR-008 留到 M5 网页编辑器阶段。
- **关键约束**: 失败降级（缺依赖/ffmpeg 不可用/某段音频读取失败 → warning 跳过 MP4，不阻断其他产物，不破坏已有 video.mp4），对齐 T-003 健壮性教训。
- **未决细节**: MoviePy 1.x/2.x API 有差异，Codex 需在 requirements.txt 锁定版本下限并在 HANDOFF 写明所用 API。
- **状态**: 采纳（落实 ADR-008，供 T-004/M3 施工）

## ADR-013 | 文案质量专项：升级 prompt 工程 + 两套可切换文案风格 + 契约加 copy_style
- **决策**:
  1. 文案专项的核心是**重写 `build_claude_instruction` 的 prompt**——从「只讲 JSON 格式约束」升级为「真正会写带货文案的创作提示词」（钩子、痛点、卖点、转化引导、平台口语化）。这是产品核心竞争力所在，不是改架构。
  2. 提供**两套文案风格**：`punchy_local`(下沉口语、前3秒强钩子、痛点直给、强转化引导) 与 `professional_trust`(专业克制、建立信任、少夸张)，prompt 按风格注入不同创作准则。
  3. 契约升级(video_project.schema.json)：config 新增可选 `copy_style` 枚举(`""`/`punchy_local`/`professional_trust`)。**为空时按 industry 自动判定**（医疗/教育/培训 → professional_trust；餐饮/零售/维修/美业/生活服务 → punchy_local）；config 显式指定则覆盖自动判定。向后兼容，旧 config 无此字段走自动判定。
  4. **mock 占位文案一并升级**：mock 也按 copy_style 产出两套风格的占位文案，让离线 demo 也能展示像样效果（用户决策）。
  5. **验收方式**：用真实 Claude API key 跑 claude provider 生成几条真实文案，人工对比 mock 占位文案，由用户主观判断质量是否提升（文案好坏无法自动化测试，用户决策）。
- **理由**:
  - 用户多次明确「真正决定视频好坏的是文案内容质量」，而非配音/渲染花哨度（HANDOFF #10 留痕）。当前 `build_claude_instruction` 的 prompt 极单薄，Claude 只会产出和 mock 同档次的「正确但平庸」文案——这是当前最大的质量瓶颈。
  - 两套风格咬合产品定位：下沉市场餐饮/零售用强钩子口语，医疗/教育用专业信任感。按 industry 自动判定降低客户使用门槛，显式 copy_style 留给需要微调的场景（也契合 ADR-002「半自动+人工品控」与 M5 编辑器可改文案）。
  - 闭环已通(M1→M3)，符合 ADR-011「闭环后回炉做文案」的时机。
- **接口变化**: 升级 schema（config.copy_style 可选字段）。这是 PM 主动升级并记入本 ADR，Codex 按新字段实现即可，不要再改契约。
- **状态**: 采纳（落实 ADR-011 文案回炉；供 T-006 施工）

## ADR-014 | 离线文案接入：file provider 人工投喂为主，中转地址可配置为辅
- **决策**:
  1. 新增 `--provider file` 模式：程序生成 `output/llm_prompt.txt`（T-006 升级后的完整提示词），用户手动喂给任意 AI（Claude.ai/网页/任何模型），把返回 JSON 存成 response 文件，重跑读回继续流水线。零 key、零成本、不挑模型。
  2. 顺手让 `--provider claude` 的接入地址可配置（环境变量 `ANTHROPIC_BASE_URL`，默认官方），使中转站/代理 key 能用——修用户当前 403 问题。
- **理由**:
  - 用户环境无官方 key、只有中转站 key，且中转站 key 打到官方端点被 403。
  - file 模式彻底摆脱 key 依赖，且完美咬合 ADR-002「半自动 + 人工品控」——「把文案交给 AI、拿回结果」本就是设计允许的人工节点。也让 T-006 升级的 prompt 不靠 key 就能落地见效。
  - 两条路互为备份：能搞定中转地址就自动化，搞不定就人工投喂，都不卡住产品验证。
  - 这是 provider 层增强，不动数据契约、不动 T-006 的 prompt 内容。
- **关键约束**: file 模式两次运行靠文件落盘衔接，--clean 会破坏 response 文件（response 建议放 output/ 外规避）；不把 key/base_url 写进日志或文件；AI 返回 JSON 可能被 markdown 包裹，读取时宽容剥壳。
- **状态**: 采纳（供 T-007 施工）
